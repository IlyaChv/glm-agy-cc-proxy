# Как пользоваться этой пачкой

Набор файлов для запуска агентной разработки в проекте: разделено по аудитории, без привязки к
стеку, у каждого правила есть цена ошибки. Формулировки выверены по официальным руководствам
Anthropic по промптингу (раздел 8).

---

## 1. Состав

| Файл | Язык | Для кого | Куда едет |
|---|---|---|---|
| `AGENTS.md` | EN | агент | корень репозитория проекта |
| `CLAUDE.md` | EN | агент | корень репозитория проекта |
| `rules/known-problems.md` | EN | агент | `.claude/rules/` проекта; грузится только при открытии файлов по `paths` |
| `rules/testing.md` | EN | агент | `.claude/rules/` проекта; грузится только при открытии тестов |
| `task-brief.md` | EN | агент + человек | `docs/templates/` проекта |
| `adr.md` | EN | человек | `docs/templates/` проекта |
| `memory-entry.md` | EN | человек | `docs/templates/` проекта |
| `agent-playbook.md` | RU | тимлид, разработчики | **общая вики или отдельный репозиторий, не в проект** |
| `README.md` (этот файл) | RU | тот, кто разворачивает | туда же, где плейбук |
| `optimizator-max/` (skill) | EN | агент | `~/.claude/skills/` разработчика; для всей команды — `.claude/skills/` репозитория |

**Плейбук не копируется в проекты.** Он один на организацию. Скопированный в десять репозиториев,
он разойдётся в десяти направлениях — ровно то, от чего он предостерегает.

**Почему агентские файлы на английском.** `AGENTS.md` грузится в каждую сессию, а кириллица стоит
в 2–3 раза больше токенов. Плюс один язык с кодом, коммитами и текстами ошибок: русская инструкция
заметно повышает шанс получить русские комментарии в коде. Методички для людей — на русском, иначе
их не читают.

## 2. Связка `CLAUDE.md` → `AGENTS.md`

Claude Code читает `CLAUDE.md`, а не `AGENTS.md`. Поэтому `CLAUDE.md` в пачке содержит
`@AGENTS.md` первой строкой — это настоящий импорт, который подставляет контракт в контекст.

Чего делать нельзя:

- заменять импорт обычной markdown-ссылкой — это просто текст, файл не загрузится;
- заворачивать `@AGENTS.md` в бэктики или код-блок — парсер импортов их пропускает;
- копировать правила из `AGENTS.md` в `CLAUDE.md` «для надёжности» — при конфликте двух
  инструкций агент может выбрать любую.

В `CLAUDE.md` живёт только поведение харнесса, а не проекта: прогресс-строки для человека, когда
звать сабагентов и на какой модели с каким effort (таблица «Models and subagents»), параллельные
вызовы инструментов, точечные правки, plan mode на критических путях. Правила проекта — в
`AGENTS.md`. Таблица моделей дублируется в плейбуке (для людей) и в скилле `optimizator-max` —
при ревизии менять все три.

Альтернатива импорту, если Claude-специфичных правил не нужно: `ln -s AGENTS.md CLAUDE.md`
(на Windows симлинк требует прав администратора — оставьте импорт).

**Проверка после установки:** запустить `/context` и убедиться, что `CLAUDE.md` есть в списке
загруженных memory-файлов. Если его там нет — агент правил не видит, и всё остальное не имеет
значения.

## 3. Установка в новый проект

Порядок важен: `/init` извлекает факты из кода, поэтому кода к этому моменту должен быть хотя бы
скелет.

1. **Скелет и Уровень 0.** Тулчейн, анализатор типов, линтер, одна команда `check`, один эталонный
   тест, скрипт подъёма окружения, CI, воспроизводимое окружение. Чеклист — в плейбуке. Стек
   выбираете вы, не агент.
2. **`AGENTS.md` в корень**, заполнить плейсхолдеры `<...>`: команды, карта модулей, скоуп,
   DoD, критические пути, файл прогресса. Команды на этом шаге уже существуют, поэтому заполняете
   фактами.
3. **`CLAUDE.md` рядом**, проверить через `/context`. Удалить строки специфики, которые не про
   этот репозиторий.
4. **`rules/` → `.claude/rules/`**, в каждом файле заполнить `paths` под реальную раскладку:
   легаси-области в `known-problems.md`, расположение тестов в `testing.md`. Файл с пустыми или
   чужими `paths` не загрузится никогда.
5. **`task-brief.md`, `adr.md`, `memory-entry.md` → `docs/templates/`.**
6. **`/init`** — пусть уточнит карту модулей и команды по реальному коду. Существующий `CLAUDE.md`
   он не перезаписывает, а предлагает улучшения. Результат переносите в `AGENTS.md` руками.
7. **Слой принуждения** (раздел 5). До этого шага все правила — рекомендации.

## Установка в существующий проект

Тот же порядок, но шаг 1 растянут: не пытайтесь закрыть Уровень 0 целиком перед стартом. Минимум —
одна команда `check` и зелёный прогон. Дальше:

- запустите `/init` **до** написания `AGENTS.md` — получите черновик карты модулей и команд;
- перенесите из него в `AGENTS.md` только факты (команды, layout), правила напишите сами;
- `.claude/rules/known-problems.md` заполняйте по мере того, как агент вляпывается в легаси:
  каждый случай — строка с владельцем и датой плюс путь области в `paths`.

## 4. Ежедневный цикл

1. **Постановка** по `docs/templates/task-brief.md`. Если контекст проработан в сессии (PRD, разбор
   бага) — попросите её написать handoff-бриф, но отревьюйте два раздела: «Do not touch» и
   «Acceptance criteria». Агент, пишущий бриф себе, систематически расширяет первый и размывает
   второй. Длинный материал — в начало брифа, задача и критерии — в конец; просите действие
   («измени»), а не мнение («предложи»).
2. **Новая сессия на реализацию.** Одна сессия — один этап. Смена задачи → `/clear`.
   Отдельная задача — отдельный worktree и ветка `agent/<имя>`. Длинная задача ведёт файл
   прогресса; следующая сессия начинает с него и `git log`.
3. **Проверка по DoD** из `AGENTS.md`: зелёный локальный прогон плюс проверка на реальности
   (живой контракт, реальные данные, UI, роли).
4. **Один MR.** Тело коммита: что / почему / как проверено. Финальное сообщение агента — что
   сделано, чем проверено, что не сделано.
5. **После инцидента или повторного исправления** — запись по `docs/templates/memory-entry.md`.

## 5. Слой принуждения

`AGENTS.md` — это контекст, а не конфигурация: агент читает правила и старается им следовать, но
гарантии соблюдения нет. Всё, что действительно нельзя допустить, закрывается механически.

| Правило из `AGENTS.md` | Чем закрывается на самом деле |
|---|---|
| Никаких write-действий без команды | `permissions.deny`, PreToolUse-хук (разворачивается скиллом `git-guardrails-claude-code`), защита веток |
| Секреты не читаем | запрет чтения `.env` и ключей в правах, отсутствие секретов в репозитории |
| Local CI is on you | pre-commit хук (скилл `setup-pre-commit`) + обязательные проверки как merge-gate |
| Ревью человеком на критических путях | CODEOWNERS, без исключений для «маленького диффа» |
| Зависимость только с разрешения | отдельный owner на lock-файлы и манифесты |
| Сабагенты — только для крупного и независимого | `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`, `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` в окружении проекта (Claude Code 2.1.217+) |

Правило большого пальца: если нарушение должно блокировать мерж — ему место в CI, а не в промпте.
В `AGENTS.md` остаётся объяснение, почему так, — оно нужно, чтобы агент не искал обход.

## 6. Поддержка

- **Бюджет.** Числового лимита на `AGENTS.md` нет. Ограничение другое: каждая строка оплачивается
  каждой сессией и ослабляет соседние, потому что модель видит все правила разом и не взвешивает
  их по важности. Отсюда вопрос к любому новому правилу: нужно ли оно каждой сессии? Если нет —
  ему место в `.claude/rules/` с привязкой к путям (`paths` во frontmatter, грузится только при
  открытии совпадающих файлов), в ADR или в локальном `AGENTS.md` подсистемы. Если да — стоит ли
  оно больше какого-то из уже стоящих.
- **Комментарии бесплатны.** Блочные HTML-комментарии вырезаются перед подстановкой в контекст —
  заметки для людей внутри `AGENTS.md` токенов не стоят.
- **Путь правила:**
  замечено дважды → memory-запись · замечено в нескольких проектах → правило в `AGENTS.md` (если
  нужно каждой сессии) или в `.claude/rules/` по путям (если только части) ·
  проверяемо машиной → линт, тест или CI-гейт, а запись удаляется.
- **Ревизия по дате в шапке плейбука** (сейчас — `2026-10`), раньше — при выходе новой модели или
  нового гайда: имена моделей и таблица их поведения (в трёх местах: плейбук, `CLAUDE.md`, скилл),
  строки `known-problems.md` без движения полгода, правила, которые уже стали автоматическими
  проверками, и правила в `AGENTS.md`, которые нужны не каждой сессии — их вниз, по путям.
  Сверять с руководствами из раздела 8: модели меняют поведение, и правило, писавшееся против
  «ленивой» модели, на новой даёт перестраховку. Перед ревизией — прогон `/optimizator-max`: аудит
  находит дрейф правил и накопленный долг вместо ручного поиска.
- **Владелец у плейбука один**, изменения — через MR с обоснованием.

## 7. Частые ошибки при внедрении

| Ошибка | Что происходит |
|---|---|
| «Сделай `/init` с учётом этих правил» на пустой папке | Сканировать нечего, получите пустышку. Сначала скелет |
| Ссылка на `AGENTS.md` вместо `@`-импорта | Контракт не загружается, агент работает без правил |
| Плейбук скопирован в каждый проект | Десять расходящихся версий за квартал |
| Правила оставлены только в `AGENTS.md` | Соблюдаются, пока удобно; на сложной задаче обходятся |
| Плейсхолдеры `<...>` не заполнены | Первая сессия уходит на выяснение, как запускаются тесты |
| В `AGENTS.md` копятся правила, нужные не каждой сессии | Каждое ослабляет остальные, включая критические; выносить по путям в `.claude/rules/` |
| `paths` в файле правил не заполнены или не совпадают с раскладкой | Файл не загружается никогда, правила из него не существуют для агента |
| Правила усилены капсом и «MUST» | Новые модели перестраховываются и спрашивают про всё; правило с «почему» работает без крика |
| Файл прогресса не заведён на длинной задаче | После сжатия контекста агент теряет, что уже проверено, и делает заново или бросает |
| Про сабагентов написаны только ограничения, без триггеров | Ведущий делает всё сам, расход летит; в `CLAUDE.md` сначала «когда делегировать», потом «когда не надо» |
| Длинный отчёт пишется одним вызовом | Ход зависает или рвётся соединение, документ теряется целиком; секции — отдельными файлами |

## 8. Откуда формулировки

Правила в `AGENTS.md`, `CLAUDE.md` и шаблонах следуют официальным руководствам Anthropic:

- общие практики: <https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices>
- Fable 5.1: <https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1>
- Opus 5: <https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5>
- Sonnet 5: <https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5>

Что именно из них применено и почему — в плейбуке: разделы «Как формулировать правила и
постановки», «Состояние — на диске» и «Выбор модели и оркестрация сабагентов». Здесь список не
дублируется: две копии разъезжаются, как и любые два файла с одними правилами.
